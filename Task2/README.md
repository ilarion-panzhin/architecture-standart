# Task 2: FURPS+ таблица требований для MVP цифровизации депозитов

## Описание задачи

В рамках проекта цифровой трансформации банка «Стандарт» необходимо подготовить структурированное описание архитектурно-значимых требований к разработке MVP функционала онлайн-заявок на депозиты.  
Требования собраны для двух каналов:
- **Сайт** — для новых клиентов.
- **Интернет-банк** — для действующих клиентов.

MVP предполагает:
- Возможность подачи заявок онлайн.
- Ручную обработку заявок менеджером бэк-офиса в АБС.
- Подтверждение операций через СМС.
- Уведомление клиента о результатах.

В процессе учтены:
- Требования бизнеса.
- Ограничения текущего IT-ландшафта.
- Законодательные нормы (защита персональных данных, шифрование трафика).
- Технологические предпочтения (использование существующих платформ MS SQL, Oracle и т. д.).

## Методика
Требования структурированы по методике **FURPS+**:
- **F** — Functional (функциональные требования).
- **U** — Usability (требования к удобству использования).
- **R** — Reliability (требования к надежности).
- **P** — Performance (требования к производительности).
- **S** — Supportability (требования к сопровождаемости).
- **+** — Дополнительные нефункциональные требования, включая ограничения, стандарты и юридические обязательства.


Требования дополнительно классифицированы по приоритету:
- **MVP** — необходимо реализовать в первой версии.
- **Позже** — можно внедрить на следующих этапах развития продукта.
- **Обязательно** — требования, выполнение которых обязательно для соответствия нормативам.

Ниже приведена полная FURPS+ таблица, включающая как базовые, так и расширенные требования с приоритетами.


| Код | Требования                         | Комментарий |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
|     | Возможность подачи заявки на депозит через сайт с указанием Ф.И.О. и телефона | Основная функция MVP для новых клиентов |
|     | Возможность подачи заявки на депозит через интернет-банк с выбором счёта и суммы | Основная функция MVP для действующих клиентов |
|     | Отображение списка доступных депозитов с актуальными ставками на сайте и в интернет-банке | Необходимая информация для принятия решения |
|     | Отображение персонализированных ставок для авторизованных клиентов в интернет-банке | Персонализация предложения |
|     | Подтверждение заявки через СМС-код в интернет-банке | Требование безопасности |
|     | Возможность обработки заявок менеджером бэк-офиса с подтверждением условий депозита в АБС | MVP предполагает ручную обработку |
|     | Отправка СМС-уведомлений клиенту после подтверждения ставки и открытия депозита | Канал информирования клиента |
|     | Возможность работы со ставками в системе для бэк-офиса депозитов и кредитов | Сейчас ставки только в XLS |
| U   | Удобство использования (Usability) |              |
|     | Интерфейс максимально удобный для клиента | Повышение удовлетворённости пользователей |
|     | Быстрый отклик интерфейса (миллисекунды) | Требование к UX |
|     | Соблюдение корпоративной дизайн-системы | Единый стиль, узнаваемость бренда |
| R   | Надёжность (Reliability)           |              |
|     | Доступность сервисов 24/7 с SLA 99,9% | Требование бизнеса |
|     | Возможность переключения интернет-банка на резервный ЦОД | Обеспечение отказоустойчивости |
|     | Избегание прямого обращения интернет-банка к API АБС в новом процессе | Снижение нагрузки и рисков отказа |
|     | Защита передаваемых данных с сайта и интернет-банка | Требование безопасности и комплаенса |
| P   | Производительность (Performance)   |              |
|     | Быстрая загрузка справочных данных (<1 сек) | Исправление текущей проблемы |
|     | Поддержка горизонтального масштабирования интернет-банка | Повышение производительности при росте нагрузки |
|     | Учёт вертикального масштабирования АБС (ограничение) | Особенности платформы АБС |
| S   | Поддерживаемость (Supportability)  |              |
|     | Использование существующих технологий (MS SQL, Oracle) | Снижение затрат и рисков внедрения |
|     | Новые технологии должны быть совместимы с текущими платформами | Минимизация интеграционных проблем |
|     | Желательна экспертиза у сотрудников по новым технологиям | Сокращение времени обучения и ошибок |
|     | Разработка документации для расширения системы | Поддержка будущих изменений |
| +R  | + Ограничения (Restrictions)       |              |
|     | СМС-функционал реализован в ядре, доработки подрядчиком нежелательны | Сокращение внешних зависимостей |
|     | Kafka предпочтительна для очередей сообщений, но несовместима с текущей версией интернет-банка | Ограничение по архитектуре |
|     | Возможный переход интернет-банка на микросервисы только для открытия депозитов | Ограничение объёма изменений на данном этапе |

# Дополнения

| Код | Требования | Комментарий | Приоритет/Этап |
|-----|------------|-------------|----------------|
| F   | Централизованный сервис аутентификации/авторизации (IAM/SSO) для сайта и интернет-банка | Единый вход: OIDC/OAuth2, единые политики паролей/сессий, меньше дублирования логики | Позже |
| F   | MFA: подтверждение операций СМС-кодом | СМС уже в ядре; оставляем СМС как MVP, закладываем расширение | MVP |
| F   | Роли и права (RBAC/ABAC) для бэк-офиса (депозиты/кредиты) | Разделение доступа по требованиям ИБ | MVP |
| U   | Единый SSO-флоу без «пере-входов» между сайт/ИБ | Меньше трения в пользовательском пути | Позже |
| U   | Безопасные «долгие» сессии с авто-продлением и принудительным выходом при рисках | Баланс UX и безопасности | MVP |
| R   | HA для IAM: минимум 2 инстанса, health-checks, zero-downtime деплой | Критичный компонент для логина/подписания | Позже |
| R   | DR-план для IAM и шлюза СМС (fallback-провайдер) | Снижение единой точки отказа | Позже |
| R   | Шифрование данных «на линии» и «на покое» (TLS 1.2+/1.3, TDE/Always Encrypted где возможно) | Чувствительные данные пользователя | Обязательно (закон) |
| P   | Кэширование справочников и ставок (in-memory, TTL) + lazy refresh | Устранение задержек >1 сек | MVP |
| P   | Партиционирование крупных таблиц (MS SQL/Oracle) и read-реплики для чтения | Совместимо с текущими СУБД; перед шардированием | Позже |
| P   | Горизонтальное масштабирование фронтов ИБ + балансировка по ЦОД | Соответствует целям по масштабируемости | Позже |
| P   | Асинхронные интеграции (очереди/шина; Kafka в перспективе) | Снять пиковую нагрузку с АБС | Позже |
| S   | Централизованное управление секретами и ключами (KMS/Vault), ротация | Сокращение операционных рисков | MVP |
| S   | Полный аудит безопасности: события IAM, заявки, ставки, СМС | Трассируемость и разбор инцидентов | MVP |
| S   | Безопасный SDLC: SAST/DAST, code review, деплой через CI/CD | Предотвращение уязвимостей на ранней стадии | MVP |
| S   | Документация по API (OpenAPI), схемы, гайды по интеграции | Упрощение сопровождения и масштабирования | Позже |
| +R  | Шардирование БД **не применяется к АБС** (только вертикальный скейл); для новых сервисов «partition-first», шардирование опционально | Ограничения стека АБС; для новых компонентов, совместимость с MS SQL/Oracle | Позже |
| +R  | IAM на базе доступной экспертизы (напр., Keycloak/ADFS), совместимость с .NET/ASP.NET MVC и текущими СУБД | Соответствие требованию «использовать то, что уже есть» | Позже |
| +R  | Политики безопасности: TLS 1.2+/HSTS/PFS, CSP, rate-limit/WAF, input validation по OWASP ASVS | Базовые практики защиты веб-приложений | Обязательно (закон) |
| +R  | Сегментация сети и principle of least privilege для доступов к АБС и хранилищам | Минимизация blast-radius при инцидентах | MVP |
| +R  | Защита ПДн: минимизация сбора, маскирование, срок хранения, права субъекта | Соответствие требованиям по персональным данным | Обязательно (закон) |
